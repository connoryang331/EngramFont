# Squircle on Line↔Curve (the Glyphs Raindrop Dot): Derive the Transition at Render and Export Time; Screen and Export Locked Together by a Shared Truth Table

> **Implementation status: landed (2026-10-15).** Render (canvas-derived path), gesture (shift+double-click sets the flag),
> and export (Python-side derivation) all share `test-common/squircle-line-curve-vectors.json` (generated by Python,
> asserted on both sides). For mirror orientation and the rescue sweep for right-angle corner seams, see "Implementation addendum" at the end.

## Background

- After [ADR-0011](0011-node-kind-state-is-geometry.md) established "state is geometry, the icon must not lie", the user
  asked to complete the last kind of seam: **a straight line joining a curve** (Glyphs' *super-smooth raindrop*; in this repo's icon system it corresponds to
  the "curvature-continuous (G2) transition curve" tier).
- **A single cubic segment cannot fit this transition — that is a mathematical fact, not a trade-off**: the straight side has curvature 0 everywhere, so G2 requires the curve side to have
  curvature 0 at the node too, i.e. `B''(0)=0 ⟺ c₁=(P₀+P₂)/2` (the midpoint rule); meanwhile G1 requires the tangent at the node to follow the line direction,
  i.e. the second control point must lie on the line. Both at once ⟹ **both control points lie on the line ⟹ that segment is a straight line**. So the
  transition needs at least **2 segments**, i.e. at least one new point.
- The Glyphs handbook's corresponding description ([handbook](https://handbook.glyphsapp.com/editing-paths/#super-smooth-nodes)):
  > "Between a curved and straight segment, a super-smooth node has a half-square/half-circle (or
  > raindrop) icon. These nodes create a smooth transition from straight line segments to curved
  > segments. … Note that such transitions require that the straight segment is not too short or
  > otherwise there is not enough room to create a smooth transition. Small gray dots on the straight
  > segment show this required space while small gray dots near the curved segment show **the points
  > that are created on export**."
- This repo's export **draws the stored path directly on the Python side** (`src/fontra/filesystem/exportmanager.py`
  `_drawGlyph()` → `sg.path.drawPoints(pointPen)`). Derivation "only in JS" therefore **never reaches the exported font**;
  screen and export must share the same source of truth, otherwise we keep paying the drift cost Glyphs has long been paying.

## Decision

### 1. The flag stays on the corner you clicked; the invariant is rewritten in terms of "regions"

The squircle flag and the superellipse icon **stay on the corner node P the user double-clicked** and do not move with the derived points (Glyphs semantics:
"this corner of mine became a superellipse corner"). The invariant therefore changes from ADR-0011's

> icon = a property of **this node's seam** (corner: straight on both sides / smooth: collinear tangents / squircle: continuous curvature vectors)

to

> icon = a property of **the regions on both sides of this node**; for curve↔curve it is still curvature-vector continuity of "this node's seam" (ADR-0010/0011
> unchanged), while **for line↔curve it means this corner region is derived into a G2 transition**.

### 2. The file is untouched; the transition is derived at render and export time

Derived geometry is **not written back into the path**: storage remains "straight line + curve meeting at P". Derivation happens only at the two consumers:

- **Canvas**: in `src-js/views-editor/src/visualization-layer-definitions.js`,
  `fontra.edit.path.under.stroke` (L1956), `fontra.edit.path.stroke` (L1974),
  `fontra.edit.path.fill` (L1913) switch to reading the **derived display path**;
  while `fontra.edit.editing.layers` (L1926) **keeps reading the original path** — derived points are therefore **not selectable and not draggable**,
  and the user always drags real control points (exactly the feel "points appear only at export" should have).
- **Export**: `_drawGlyph()` in `exportmanager.py` swaps in the derived path before `drawPoints`;
  TTF / OTF / WOFF2 share this one spot, so a single change covers all of them.
- The Python side already recognizes the flag (`PointType.ON_CURVE_SQUIRCLE = 0x18` in `src/fontra/core/path.py`).

### 3. The derivation's construction: three points and two segments, E → M → P

> ⚠ **The construction in this section has been falsified by a numerical prototype and awaits revision** (`qa/probe-raindrop.py`, 2026-10-15).
> The problem: making the end of the transition segment **inherit the original curve's two handles** (`seg2 = [M, hC, Y, P]`) is wrong — the original curve's near-end
> handle Y sits **ahead of** P, so the transition segment arrives at P traveling in the **−x** direction while the original curve leaves P in **+x**;
> the derived outline **reverses direction** at P (cusp/self-intersection), and the curvature vector at P has the opposite sign of the original curve's.
> Numerical evidence: a solution does exist (residual ~1e-16, curvature jump at M ~1e-19), but `s = −0.44` (M lands on the other side of the line)
> and `seg2 @P: k = −5.05e-03` vs the original curve's `+5.05e-03` — **same magnitude, opposite sign**.
> Revision direction: the transition should **swallow P and rebuild the entire corner region**, which matches Glyphs' model
> ("the original path is shown in gray, the smoothed path drawn separately"). Do not implement per this section before the revision.
>
> **The revised construction skeleton** (pending prototype validation): the derived outline is
> `… A —line— E —seg1→ M —seg2→ Q —remaining original curve→ C …`, where `Q` is obtained by an exact de Casteljau split of the original curve
> `[P, Y, hC, C]` (parameter `q`), giving the two halves
> `[P,Y,hC,Q]` and `[Q,·,·,C]`; after `Q` comes the second half ⟹ the travel direction no longer reverses.
> - Conditions: **G1+G2** at `E` (with the line), **G1+G2** at `M`, **G1+G2** at `Q` (with the remaining original curve)
> - Unknowns: `q`(1) + the position of `c2'` on the line(1) + `M`(2) + the two control points of `seg2`(4) = **8**;
>   the two constraints at `E` are consumed by construction (`c1'=(E+c2')/2` and `c2'` on the line), leaving **6 degrees of freedom / 5 conditions** ⟹ about 1 spare degree of freedom
>   for shape plausibility (M's orientation, avoiding self-intersection)
> - Solving: a 6×5 nonlinear system ⟹ needs Newton with step-size backtracking + a numerical Jacobian, and **must** come with shape-plausibility
>   checks (self-intersection, which side of the line M is on); failing them means rejection (not enough room / no solution)
> - What is already confirmed feasible: G1+G2 at `E` is **exact by construction** (jump 0), and the deterministic scan+bisection in the prototype
>   pushed the residual at M down to the `1e-19` order ⟹ numerically feasible; what is missing is the robustness of the topology and of the multi-unknown solve
> - **v2 prototype progress** (`qa/probe-raindrop-v2.py`, 2026-10-15): the topology passes — the ASCII outline shows the derived path advancing
>   monotonically `E → M → Q → C`, **no cusp, no reversal, no self-intersection** (exactly where v1 failed).
>   Condition convergence: the initial guess already satisfies the four conditions `G1@M`, `G1@Q`, `G2 direction@M`, `G2 direction@Q` (residuals ~1e-16),
>   with **only the two curvature-magnitude conditions** unsatisfied (`G2 magnitude@M ≈ −0.84`, `G2 magnitude@Q ≈ +0.94`) ⟹ the actual solve size
>   is far smaller than 8 unknowns. But the prototype's least-norm + normal-equation Gauss solve hits a **singular Jacobian** at the initial point,
>   so Newton never really starts ⟹ **the current conclusion is "solver failure", not "mathematically infeasible"**; feasibility remains undetermined.
>   Next step: switch to a solve with steadier damping (Levenberg–Marquardt, or nested bisection on the two magnitude conditions),
>   then add self-intersection and M-orientation checks. **Do not enter implementation before that.**
>
> - **v2b prototype progress** (`qa/probe-raindrop-v2b.py`): `G1@M` and `G1@Q` were changed to be **satisfied by construction**
>   (`g1 = M + s·(M−c2)`, `g2 = Q − v·(half[1]−Q)`), so the remaining two curvature-magnitude conditions each contain a single unknown,
>   solved one by one via "sign-change scan + bisection" ⟹ **no Newton, no singularity**.
>   Convex quarter-arc fixture result: `q=0.35, s=1.0519, v=0.4553`, `G1@M = +2.05e-17`, `G1@Q = −4.97e-17`,
>   **curvature at `E` 0.000e+00 (vs the line)**, **at `Q` 2.102868e-03 vs 2.102868e-03 exactly equal**;
>   the ASCII outline is monotonically smooth, no cusp/self-intersection/reversal.
>   ⚠ **One item unfinished**: the magnitude at `M` did not match (`4.7616e-04` vs `8.6928e-04`). Root cause located: when solving
>   `s`, a "bending direction mismatch" was encoded as `None` in the residual function, so the scan **steps across the undefined interval** and picks a wrong bracket
>   (the shallow-arc fixture even produced a wrong-sign solution). Fix: **do no direction check inside the magnitude residual** (direction is checked only at final acceptance,
>   and that interval is marked unavailable), or track the sign explicitly before bisecting.
>   **Status: of the three seams, `E` and `Q` hold exactly, `M` is unsolved ⟹ still no implementation.**
>
> - **v2b correction and conclusion** (`qa/probe-raindrop-v2b.py`): the "solve one at a time" approach above was **wrong** — the curvature at
>   `M` depends on **both** handles of `seg2` at once (`B''(0)` contains `g2`), so `s` and `v` are **coupled**, and solving them one after the other
>   independently necessarily yields wrong roots. Changed to a **2×2 damped Newton** on `(s, v)` (G1 is satisfied by construction, leaving a 2×2 system).
>   After the fix, measured:
>   - Convex quarter-arc: **all three seams exact** — `@E 0.000e+00 vs line 0`,
>     `@M 5.294238e-04 vs 5.294238e-04`, `@Q 1.528033e-03 vs 1.528033e-03`,
>     with `G1@M/@Q` residuals `~5e-17`; the ASCII outline is monotonically smooth
>   - **The expectation "the curve has an inflection near P ⟹ reject" was overturned**: this fixture also solved, with all three seams exact.
>     The reason is that after rebuilding the corner region we no longer depend on the original curve's local behavior ⟹ **the rejection condition cannot hinge on the inflection**;
>     it can only hinge on **insufficient room** (the straight side too short) and on solver failure
>   - ⚠ **Still open**: the shallow-arc fixture found **no solution** on the 252-point `(q, mFrac)` grid. It is the geometrically easiest case,
>     so this is more likely a grid-coverage / initial-value problem than true infeasibility ⟹ "no solution" and "not found" must be distinguished before drawing a conclusion.
>   **Status: both feasibility and the solver are validated (one case fully exact; one fully exact and overturning the expectation), but the decision rule and the distinction from "no solution"
>   are unfinished ⟹ still no implementation.**
>
> - **v2b multi-start + shape checks** (per case, 23×16×6 = **2208** `(q, mFrac, initial value)` attempts):
>   - Convex quarter-arc: **35 runs converged, all 35 passed the shape checks** (no self-intersection; `M` on the same side as the line),
>     and the selected solution has all three seams exact: `@E 0.000e+00`, `@M 6.683153e-04 vs the same value`, `@Q 1.067510e-03 vs the same value`,
>     with `G1` residuals `~1e-16`
>   - Inflection fixture: **14 runs converged and all passed the shape checks**, three seams exact (again confirming that the inflection is **not** a rejection condition)
>   - Shallow-arc fixture: **0 / 2208 converged** ⟹ most likely genuinely infeasible under this construction (a shallow arc must climb from 0 curvature to
>     that very small curvature value), but **not yet proven**
>   ⚠ **Two items left unfinished this round** (to be completed next round):
>   ① The **failure-reason labels of individual attempts are not wired up** (all empty strings in the stats) ⟹ "not found" and "no solution" are still not truly separated;
>      first confirm whether the shallow-arc attempts hit an "early return" or "Newton genuinely fails to converge";
>   ② The shape filter **has never rejected any candidate** (0 rejections) ⟹ as a filter it **has not been genuinely exercised**; build a deliberately self-intersecting sample
>      to confirm it would be caught.

Take as an example a straight line A…P joined to a curve P→Y→hC→C (P is already smooth, so the curve's tangent at P follows the line):

| Point | Property | Conditions satisfied |
|---|---|---|
| **E** (new, on the line, at distance t from P) | the straight segment A…E stays straight | seam with the line **G1 (tangent along the line) + G2 (midpoint rule ⟹ curvature 0 at the node)** |
| **M** (new, the transition apex) | two cubic segments, E→M and M→P | **G2** with the E segment, **G2** with the P segment (2 conditions each) |
| **P** (existing, **untouched**) | the original curve P→Y→hC→C is not changed by a single bit | at its end **tangent = the original curve's tangent at P**, **curvature = the original curvature κ_P** |

The unknowns — `t` and the position of `M` — total 4 degrees of freedom against 4 conditions ⟹ solvable; reuse the
**deterministic sign-change scan + bisection** recipe already validated in `slideNodeForG2()`. **P and its original curve are not replaced at all** — the shape the user drew is preserved as-is,
with only a transition segment added at the corner.

### 4. Room check: insufficient room means rejection

Following the idea of `lineToCurveRoom()`, compute the admissible setback distance for E: if the straight side is too short ⟹ the transition has nowhere to unfold ⟹
**no flag, no derivation, no file change** (consistent with "the icon must not lie"). When room is insufficient, the canvas must make the reason visible (see §6).

### 5. Single-master glyphs only

The gesture acts on the editing layer of the current master; in a multi-master glyph, "deriving" would mean **only one master's outline changes**,
while the other masters keep their sharp corners ⟹ both visuals and interpolation break (the Glyphs handbook also warns about superfluous points vs.
outline compatibility). Therefore: **when the master count > 1, reject and explain why**; no cross-master point insertion.

### 6. Screen ≡ export: one truth table, two implementations, locked down by CI

This is the **hard requirement** of this ADR (the user's exact words: "screen and export must be consistent"). The approach is not "two implementations kept in sync by discipline",
but making inconsistency **unable to pass the tests**:

- Add a shared truth table `test-common/squircle-line-curve-vectors.json`: a set of cases, each with the
  **input** (the full coordinates and flags of a line↔curve seam) + the **expected output** (the derived E and M coordinates, the G1/G2 residuals,
  and `refused` expected for the "should be rejected" cases).
- **The Python side is the reference implementation** (export follows it) and generates the truth table; **the JS side asserts against the same table**.
- Unit tests on both sides read this file: `npm test` (`src-js/fontra-core/tests/`) and
  `pytest test-py/`. If either side drifts ⟹ **the tests go red**.
- It follows the repo's existing convention: `test-common/path-change-test-data.json` is already a fixture shared between JS
  (`tests/test-path-changes.js`) and Python (`test-py/test_path_changes.py`).

### 7. Gray-dot visualization (Glyphs' two small gray dots)

The derivation must be **visible**, otherwise the user cannot tell why the outline changed or why the conversion was rejected:

- On the straight side, draw "the space needed" (E's position and the available setback distance);
- On the curve side, mark "the points that will be added at export" (M's position).

Draw them on a read-only layer (not selectable); they never enter the editing model.

## Rationale

1. **It satisfies the user's hard requirement**: screen/export consistency is guaranteed by a **shared truth table + tests on both sides** — a CI fact rather than a
   discipline convention; this is exactly what Glyphs never solved well (it stores the original and displays the derived, letting human eyes discover the inconsistencies).
2. **The file stays lean**: Glyphs' choice is "original path + derived display", because its format cannot store points that exist only at export time;
   since we are following it, we also accept the premise "the file holds the simple form", avoiding an exported font that looks different from the source file.
3. **The editing model is untouched**: derived points exist only on the render/export ends, and the user always drags real control points ⟹ the counterintuitive
   "I dragged a derived point but the file did not change" cannot happen.
4. **Start single-master**: cross-master point insertion is a separate and larger capability (it needs cross-master editing) and is out of scope for this round;
   an explicit rejection is more honest than half-support.

## Rejected alternatives

- **Flag-only (the current behavior)**: explicitly rejected by the user — "the icon becomes a square while the segment is still a curve; this looks like the icon's mark and the
  segment do not match".
- **Materializing E and M into the path at edit time**: screen/file/export would be consistent by construction, and the interpolation risk is already blocked by §5's single-master restriction.
  The user chose Glyphs-style derivation (the file keeps the simple form), so this is rejected; but if the derivation pipeline ever proves too costly, it is a fallback to return to.
- **Two implementations synced by discipline (no truth table)**: screen ≠ export is precisely the drift to avoid, and the drift only surfaces after export,
  which makes it extremely hard to debug.
- **Deriving in JS and uploading the outline with the export request**: it changes the export protocol and makes the server trust client geometry — more cost and risk than the derivation itself.
- **Forcing a single cubic segment** (take G2 with the midpoint rule, sacrifice G1): exactly the option ADR-0010 §6 already rejected; it leaves
  a seam where "the icon says G2 while the geometry has a corner".

## Consequences

- **No file-format change, no migration**; the semantics of `SQUIRCLE_FLAG` (0x18) are extended: on a line↔curve seam it means
  "this corner region is curvature-continuous (G2)", while on curve↔curve it still means "this node's seam has continuous curvature vectors".
- **Render**: the three path layers read the derived path; the editing layer stays as-is ⟹ **derived points are not editable**.
- **Export**: one change in `_drawGlyph()` covers all formats.
- **Interpolation**: no effect on single-master glyphs; the gesture **is rejected** on multi-master glyphs.
- **Hit testing and dragging**: still based on the original path (derived points are not in the model), as intended.
- **Documents needing synchronized revision**: the non-goal entry of `docs/specs/11-squircle-nodes/PRD.md` —
  "no Glyphs-style visualization of the small gray dots added at export" — is **overturned** by this ADR; ADR-0010 §6 describes the **current** behavior,
  and once this lands it needs a revision pointer to this document.

## Implementation addendum: mirror orientation and the rescue sweep (added when this landed)

Implementation uncovered and filled in two things this document did not foresee; both are now in the shared truth table:

1. **Mirror orientation** (curve first, straight line after): the same solver runs on the **control-point-reversed** slice
   (`[P, h₁, h₂, C]`); the derived run is reversed as a whole and replaces `[C, h₂, h₁, P]`, with node P unmoved.
   Truth-table case: `path-convex-quarter-arc-mirrored` (the expected outline is exactly the canonical one reversed point by point).
2. **Rescue sweep**: the neighboring-corner seam produced by smoothing a rectangle corner (a right angle, near handle on the chord) has an extremely narrow
   convergence basin that the main grid (23×16×6) happens to straddle — the feasible solution sits at q≈0.85, while the main grid samples only 0.84/0.88, so both fail to converge.
   **After the main grid dies out**, a second sweep runs with a finer q step (0.025, 37 points) to widen the Newton initial values; it triggers only when the main grid has no solution,
   so every result on existing geometry stays bit-for-bit identical (the only table change is `tiny-setback`'s attempts 2208→8128,
   honestly reflecting the extra attempts). Truth-table case: `path-right-angle-corner-raindrop`. Python/JS use the same order and the same implementation,
   with a coordinate difference between the two sides of <1e-9.

Insufficient room (`no-room`) is still rejected **before** solving and is unaffected by the rescue sweep. The feasibility-boundary investigation of the rescue sweep lives in
`qa/explore-feasibility.py` and `qa/factcheck-py-derive.py` (direct evidence that both implementations agree on verdicts).
